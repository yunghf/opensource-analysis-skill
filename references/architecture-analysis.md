# 角度一：架构实现分析（详细方法）

目标：回答"代码是怎么组织的、为什么这么组织、数据怎么流"。所有结论必须带文件路径与代码证据。

## 1. 分层识别

按"职责"而不是按目录名判断分层。识别四类常见层：

| 层类型 | 特征 | 识别线索 |
| --- | --- | --- |
| 基础层/核心层 | 不含业务词，可被多个上层复用 | 包内找不到任何领域类型名；被多个领域 import |
| 领域层/业务层 | 含业务词汇与业务规则 | 出现业务实体名；声明文件（model.yaml 等） |
| 应用/协议层 | 对接外部框架的适配 | provider、adapter、loader、manifest |
| 展示层 | 前端/工作台 | app/、static/、presentation_* |

**验证分层的判据（重要）**：
- 依赖方向是否单向：grep 检查"基础层代码里是否出现领域词汇"（越界即分层失效）。
- 复用证据：同一基础层是否被多个领域复用（目录同构是直接证据）。
- 扩展点：基础层是否为领域预留钩子/插槽（继承 + 可覆写方法、resolver、动态注册）。

## 2. 结合机制（层是怎么连起来的）

对每个结合点回答三件事：声明在哪、组合/解析在哪、绑定/执行在哪。常见模式：

- 声明文件 + 组合函数：如核心 ontology + 领域 runtime 段合成最终 ontology（注意检查是否禁止覆盖核心定义、是否剥离私有字段）。
- 字符串引用 + 动态导入：`module:function` 经 importlib 解析——"注册从改代码变成改声明"。
- Provider/Registry 协议：load_ontology + register 两步；resolver 插槽让领域插入能力。
- 继承钩子：基类定义可覆写方法，领域子类 super() 后追加领域逻辑。

## 3. 数据流

画一条"从请求到落盘"的完整链路，每一步标注文件:方法。模板：

```
输入（LLM 对话 / 表单 / API）
  → ① 入口与参数校验         file: method
  → ② 意图编译/DSL 解析       file: method（声明来源：xxx.yaml）
  → ③ 预览/校验（不落盘）     file: method（校验器名）
  → ④ 确认闸门（令牌/人工）   file: method
  → ⑤ 原子写入 + 审计         file: method（事务/审计表）
```

标注每一步属于哪一层。找出"可信写入链"的每一道闸门（预览一致性、令牌一次性、前置条件重验、记录版本比对）。

## 4. 校验与守护体系

列层次表：每一层校验器守什么（如：①本体契约只能有固定抽象类 ②实例记录契约 ③领域模型声明合法性 ④数据 vs 领域模型语义）。说明"存储通用、语义由领域解释"这类分层在数据侧的体现。

## 5. 架构评估

优势与代价各至少 2 条，且每条都要有代码依据。常见维度：复用性、依赖方向、写入可信、可演化性 vs 性能（全表扫描/写放大）、语义治理成本、无显式迁移工具。

## 6. 报告结构模板

```
# <项目>架构实现分析报告
> 分析对象 / 日期 / 结论先行
1. 仓库总览与职责分配（目录树 + 分层图）
2. <基础层>：只懂机制不懂业务（文件职责表 + 核心抽象代码）
3. <领域层>：只声明语义不写机制（声明文件示例）
4. 结合机制（声明→组合→绑定→钩子）
5. 数据流：一次操作如何贯穿各层
6. 校验/守护体系
7. 架构评估（优势/代价双栏）
8. 结论
```
