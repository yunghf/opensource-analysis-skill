# 角度四：设计巧思深挖（详细方法）

目标：找到代码里"防住了什么不可靠性、支撑了什么可演化性"的精彩设计，每个都要解释"为什么必然"。

## 1. 逐层深挖清单

按以下分层逐个找巧思（至少覆盖 3 层，≥8 项）：

| 层 | 找什么 |
| --- | --- |
| 存储/持久化层 | 软删除、ID 复用防护、版本号/修订、乐观锁、批量 vs 增量写入、部分索引、WAL、schema 自动迁移 + 版本白名单、历史表物化（backfill） |
| 事务/工作区层 | 跨介质"联合事务"（文件+DB）、before/after 审计快照、预览一致性（摘要比对）、原子文件写（tempfile+fsync+replace）、分级加载 |
| DSL/编译层 | 微型表达式（$ 前缀）、哨兵对象（区分未提供与 None）、令牌生命周期（预览 token）、可解释的不可执行原因、动态枚举注入 |
| 领域业务层 | 状态由流水/金额推导（状态不撒谎）、守恒审计（金额/额度/借贷平衡）、审计返回中间账本（可解释修复）、来源可追溯规则、浮点容差 |
| 外部集成层 | 读投影不污染本体、外部依赖静默降级 + 来源标注、分块请求 + 缓存、用图语义补缺失数据（祖先坐标）、事件化排序 |
| Agent/协议层 | resolver 插槽、依赖链自动执行、统一错误 JSON 包装、规则引擎（不交给 LLM 推理）、prompt 全量前置注入、动态工具目录、优雅降级（无凭据仍可用）、写确认通道、可插拔数据源 |

## 2. 每个巧思的记录模板

```
#### 巧思 N：<一句话名字>
- 位置：file.py::method
- 代码证据：核心片段（3~10 行，引用真实代码）
- 做什么：1~2 句
- 为什么必然：它服务于哪条基本事实，防住了什么不可靠性/支撑了什么可演化性
```

**"为什么必然"必须写**——没有解读的代码摘录不算巧思。

## 3. 巧思检查清单（读代码时对照找）

- [ ] 删除是否可恢复/可审计（软删除而非物理删除）？
- [ ] 创建是否防止 ID 重用（历史身份永续）？
- [ ] 写入是否有增量约束检查（如 SQL 递归环检测，而非只靠全量校验）？
- [ ] 并发控制是否可定位（错误告诉"哪条记录冲突"）？
- [ ] 状态是否有推导裁判（金额/流水推导状态，存储值说谎即报错）？
- [ ] 是否有预览/确认/令牌机制（不直接落盘）？
- [ ] 声明与实现是否解耦（字符串引用 + 动态加载 / resolver 插槽 / 动态 enum）？
- [ ] 是否有优雅降级路径（外部 API 失败、配置缺失、无凭据）？
- [ ] 错误与审计是否对"非专业调用者"可解释（命中字段、blocked_reasons、结构化账本）？
- [ ] 性能手段是否避免污染抽象（适配器扩展而非新概念）？

## 4. 收尾

- 制作"巧思 → 基本事实"映射表（与角度三闭环）。
- 用一句话综合：这些巧思不是炫技，而是把<根本问题>从<表示/写入/审计/解释/演化>五个维度都解到了最优解。

## 5. 报告章节模板（与角度三合并时）

```
1. 第一性原理回顾：三个基本事实
2. 代码巧思全景（按层小标题，每层多个可折叠巧思卡）
3. 巧思 → 基本事实映射表
4. 综合结论
```
