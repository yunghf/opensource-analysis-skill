# Deep Project Analysis — 主流程 Step 0~8 完整规范

> 本文件是 opensource-x skill 的主执行流程。`scripts/fetch_repo.py` 位于**本 skill 目录**的
> `scripts/` 下（例如 `~/.workbuddy/skills/opensource-x/scripts/`），以 skill 根目录为基准解析，
> 不要写死绝对路径。其余引用（`references/*.md`、`assets/report-template.html`）均相对本 skill 根目录。

对任意代码仓库做一次完整的深度分析，产出与 UOM 项目分析同等质量的成果：**每份结论都有代码证据，每个分析角度都有对应报告，每份报告都有 Markdown 与自包含 HTML 双产物**。

## 触发场景

- 用户给出 **GitHub / Gitee 仓库链接**（或本地仓库路径），要求"分析 / 读懂 / 拆解 / 解构某个项目"
- 用户要求"写分析报告"、"做架构评审"、"代码审计"、"技术尽调"、"评估代码质量"、"拆解技术栈"
- 学习明星项目源码、为二次开发做前置调研、面试前建立项目全局认知
- 新接手一个代码库，需要系统化理解并沉淀文档
- 需要对已有分析补充"演化历史""第一性原理""设计巧思"等更深角度

## 工作流总览

```
输入：GitHub/Gitee 仓库链接，或本地仓库路径
  ⓪ 接入门（G2 阻塞）——用原生候选项一次问完 4 项：分析目标 / 深度档 / 产物形态 / 数据通路
  ① Step 0  接入与摸底：获取源码 → 目录测绘 → 出「仓库总览卡」（G1 通报，不阻塞）
  ② Step 1~4  四角度分析（必须全部完成，G0 静默连跑）
  ③ Step 5~6  代码质量评估 + 技术栈拆解（两项评估，按需可只做其一）
  ④ Step 7  产物生成（形态由用户在接入门选定：HTML / Markdown / SVG）
  ⑤ Step 8  校验与交付（含"哪些门未经确认"的声明）
```

**门位规则**：全程只有 **1 个阻塞门（接入门）**，其余为 G1 通报。必须升级为阻塞门的三种例外（范围超预期 / 数据不可得 / 目标变更）见 `interaction-gates.md` §2。

**铁律：**
1. 所有分析结论必须引用具体文件路径与代码行/片段，不允许空泛表述。
2. 四个分析角度一个都不能少；每个角度产出一份报告（部分角度可合并，见下）。
3. 代码质量与技术栈两项评估必须给出**实测数字**，工具不可用时标注"未采集"并附采集命令，禁止估算。
4. **产物形态由用户在接入门决定**（HTML / Markdown / SVG，见 `output-formats.md`）；未选定则取默认 `Markdown + HTML`。**形态只改载体，不改分析深度与报告数量。**
5. 额外必须交付一份**项目全景思维导图**（规范见 `mindmap-spec.md`），其节点只允许引用报告已有结论。
6. 产物统一放入项目根 `analysis/` 目录（若项目已有 `docs/` 约定，可放入 `docs/analysis/`），文件名以项目名做前缀。
7. 交互必须走 `interaction-gates.md`：附着选项一次问完、不逐阶段打断、订正只重跑下游。
8. 完成 HTML 后必须跑校验（见 `## Step 8 · 校验与交付`），校验失败视为未完成。

## Step 0 · 接入与摸底（先摸清项目是什么）

### 0.0 接入门（G2 阻塞，唯一必须停下的地方）

**拿到仓库链接后不要立刻开跑。**按 `interaction-gates.md` §3，用宿主原生候选项**一次问完 4 项**：

| # | header | 题面 | 选项 |
|---|--------|------|------|
| 1 | 分析目标 | 你主要想拿这份分析做什么？ | 读懂源码设计 / 评估能否二开 / 面试快速准备 / 技术尽调选型 |
| 2 | 深度档 | 要挖到多深？ | 标准四角度 / 快速总览 / 全量（加质量+技术栈）/ 聚焦单一角度 |
| 3 | 产物形态 | 分析报告要什么形态？ | HTML + Markdown / 只要 Markdown / 只要 HTML / 加出 SVG 图（见 `output-formats.md`） |
| 4 | 数据通路 | 怎么拿源码？ | 直连拉取 / git 克隆（要演化分析必选）/ 我提供本地路径 / 你先看仓库再说 |

- 每个选项的描述必须写"选了会怎样"，不能只写名词。
- 用户直接甩链接不给答复、或宿主不支持候选项 → 取默认值（标准四角度 + HTML&Markdown + 直连拉取）开跑，并在交付时声明。
- 用户说「你定 / 都行」→ 切 `autopilot`（见 `interaction-gates.md` §5），但下面三种情况**仍然必须停**。

### 0.1 获取代码

优先用**不依赖 git 的直连通路**（脚本已实测：103 文件 / 13.2s / 零失败）：

```bash
# 路径解析：fetch_repo.py 位于本 skill 的 scripts/ 目录下，以 skill 根目录为基准
SC="<本 skill 根目录>/scripts"    # 例如 ~/.workbuddy/skills/opensource-x/scripts
command -v cygpath >/dev/null && SC=$(cygpath -m "$SC")   # Git Bash / Windows 下转 POSIX 路径

python "$SC/fetch_repo.py" <仓库URL> --out <目录>     # 全量（默认 max-files=300）
python "$SC/fetch_repo.py" <仓库URL> --meta-only      # 只要元数据 + 文件树（约 1 秒）
```

需要**提交历史**（角度二）时才用 git：`git clone --filter=blob:none <url>`（浅克隆必须 `git fetch --unshallow` 或 `--deepen=N` 补齐）。

- 少量单点读取（README、元数据、某关键文件）用网页读取能力（WebFetch / curl），不要为此拉整棵树；批量与统计一律用脚本（结果要落盘）。
- 无法获取时按 `repo-acquisition.md` §6 逐级降级，并把**实际通路**写进报告"数据来源"。
- 三种必须停下来问用户的例外：**范围超预期**（blob > 5,000 / `truncated` / 预计 > 3 分钟）、**数据不可得**（私有/限流）、**目标变更**。

### 0.2 预检

按顺序执行，用最少时间建立全局视图：

1. **读 README 与入口**：`README.md`、`*.md`（docs/ 下）、`.env.example`、`.gitmodules`（子模块）。
2. **目录结构**：`ls` / `find`，记录顶层包/目录及其一句话职责；识别是否分层（基础层/领域层/应用层/第三方协议层）。
3. **语言与依赖**：`pyproject.toml` / `package.json` / `Cargo.toml` 等；运行方式、端口、命令。
4. **git 历史规模**（仅 git 通路可用）：`git log --oneline --all | wc -l` 与 `git log --format="%h %ad %s" --date=format:"%Y-%m-%d"` 全量列表——这是演化分析（角度二）的原料。**直连拉取无 `.git` 时跳过此项**，并在报告中声明角度二不可用（或按 `repo-acquisition.md` §6 降级为"版本与设计演进回顾"）。
5. **文件树**：直连通路直接用 `_fetch/tree.json`（含尺寸），无需再请求 API。

预检产出：一段"仓库总览"（仓库名、定位、许可证、目录树 + 分层判断 + 依赖 + 提交数/时间跨度、构建运行方式），直接复用进报告一的开头。

### 0.3 摸底通报（G1，不阻塞）

给用户一张 ≤60 行的**摸底通报卡**（格式见 `interaction-gates.md` §4），并用宿主内联可视化能力（若有）当场渲染一张「仓库总览卡」（定位 / 语言构成 / 分层初判）——**不要等文件生成才让人看到东西**。

同时：**主动告知下一步要做什么、预计产出几份报告**，然后直接进入 Step 1（除非用户喊停）。只有 §0.1 的三种例外才升级为阻塞门。

## Step 1 · 角度一：架构实现分析

**目标**：回答"代码是怎么组织的、为什么这么组织、数据怎么流"。

方法（详细规范见 `architecture-analysis.md`）：
1. 识别分层与各层职责（对照源码逐文件归类，不猜）。
2. 找出层间"结合机制"：声明文件（yaml/json/DSL）、组合函数、provider/注册器、钩子/继承扩展点。
3. 画关键数据流：从用户意图/请求到持久化的完整链路，标注每一环所在文件。
4. 找校验/守护体系：schema 校验、前置条件、事务、审计、权限。
5. 架构评估：优势（复用、可信、依赖方向）与代价（性能、写放大、语义治理）。

**必须回答的问题清单**（缺一不可）：
- 每层文件的职责表格（文件 → 职责 → 关键点）
- 分层成立的证据（依赖方向单向性；有没有"基础层引用领域"的越界）
- 一次完整数据流（带文件引用）
- 校验体系的层数与每一层守什么
- 至少各 2 条优势与代价

产出：`analysis/<项目>架构实现分析.md` + `.html`。

## Step 2 · 角度二：git 演化分析

**目标**：回答"这套架构是怎么演化来的"，从提交历史还原设计演进。

方法（详细规范见 `evolution-analysis.md`）：
1. 全量 `git log --all --reverse`（含日期），按时间分阶段（范式切换/重构/新增领域/文档沉淀）。
2. 识别关键提交：重命名级重构、范式切换（如"表模型→图模型"）、解耦/拆包提交。
3. 对关键提交逐个 `git show --stat` 与 `git show` 关键文件 diff，提炼：哪些文件被拆、哪些语义被移动（下移/上移）、注册方式如何泛化。
4. 用"重命名对照表"记录单体→分层时路径与职责的变化。
5. 总结演化规律：维度对比表（演化前 vs 演化后）+ 驱动力量（范式觉醒/工具驱动/领域需求反向驱动基础层）。

**必须回答的问题清单**：
- 完整时间线（提交号+日期+阶段标签）
- 至少一个"决定性重构"提交的逐文件分析
- 至少一条"领域需求反向驱动基础层"或等效的抽象下沉证据
- 演化规律对比表（≥6 个维度）

产出：`analysis/<项目>基础层与领域模型演化分析.md` + `.html`（非分层项目可命名 `<项目>架构演化分析.md`）。

> 无 `.git`（tarball 降级）或浅克隆未补齐时，本角度改为"版本与设计演进回顾"（依据 release notes / CHANGELOG / tag 差异），并在报告开头声明依据来源。

## Step 3 · 角度三：第一性原理分析

**目标**：回答"这个系统在为谁解决什么不可回避的问题？"，回到不可再分的基本事实，再推导哪些设计是必然的。

方法（详细规范见 `first-principles.md`）：
1. 识别系统面对的根本问题（例如：不可靠的 LLM 要可靠地操作系统化业务）。
2. 归纳 2~4 条**不可再分的基本事实**（本体论/认知论/工程论层面各一）。
3. 从每条基本事实推导必然设计（用代码验证，而不是空谈）。
4. 诚实列出代价与边界（第一性原理要求直面缺陷）。

**必须回答的问题清单**：
- 根本问题一句话
- 基本事实 2~4 条（每条附一句"它推翻了什么表面答案"）
- 每个必然设计对应至少一处代码证据
- 至少 2 条代价

产出：并入报告三（与角度四合并），或单独一份 `analysis/<项目>第一性原理分析.md` + `.html`。

## Step 4 · 角度四：设计巧思深挖

**目标**：找到代码里"防住了什么不可靠性、支撑了什么可演化性"的精彩设计，并解释为什么必然。

方法（详细规范见 `design-wisdom.md`）：
1. 逐层深挖：存储/持久化层、事务/工作区层、DSL/编译层、领域业务层、外部集成层、Agent/协议层。
2. 对每个巧思记录：文件+方法、核心代码片段、**"为什么必然"**解读（它服务于哪条基本事实）。
3. 检查清单（找这些模式的代码证据）：
   - 软删除 + ID 永不重用 / 历史不可抹除
   - 双写入路径（bulk 重建 vs 增量变更）与写放大控制
   - 乐观并发控制（版本号/摘要比对）与可定位错误
   - 写入时的增量约束检查（如 SQL 递归环检测）
   - 状态由流水/事实推导（状态不撒谎）
   - 预览/确认/令牌（preview token）机制
   - 声明与实现解耦（`module:function` 字符串、resolver 插槽、动态枚举注入）
   - 优雅降级（外部依赖失败/配置缺失不击穿主功能）
   - 为 LLM 设计的可解释性（命中字段、blocked_reasons、结构化错误）
4. 巧思必须映射回基本事实（角度三），形成闭环。

**必须回答的问题清单**：
- 巧思 ≥ 8 项，覆盖 ≥ 3 层
- 每项含代码证据 + "为什么必然"
- 一张"巧思 → 基本事实"映射表

产出：`analysis/<项目>第一性原理与设计巧思分析.md` + `.html`（推荐与角度三合并，章节为：基本事实 → 巧思全景 → 映射闭环 → 结论）。

## Step 5 · 代码质量评估

**目标**：回答"这代码能改吗、从哪改"，把主观印象换成可复现的指标与可排序的清单。

方法（详细规范见 `code-quality.md`）：
1. 先用 `cloc` / `scc` 做规模与语言构成统计，**声明排除目录**（`.git`、`node_modules`、`vendor`、生成代码）。
2. 按语言选工具链采集指标：圈复杂度、函数/文件规模、重复率、测试覆盖率、循环依赖、静态检查告警、依赖漏洞。
3. 做"复杂度 × 变更频率"交叉分析（`git log --since="1 year ago" --numstat`）定位真正的重构靶点。
4. 按 P0（正确性/安全）/ P1（可维护性阻塞）/ P2（整洁度）分级输出改造清单。

**必须回答的问题清单**：
- 指标总览表（每项含实测值与档位判定）
- 复杂度热点 Top-10（含文件路径与 CC 值）
- 重复率与循环依赖的具体位置
- 覆盖率数字与未覆盖的关键模块
- P0/P1/P2 改造清单，每条含文件路径与影响面

产出：`analysis/<项目>代码质量评估.md` + `.html`（若项目含多种语言，按语言分节）。

> 用户只做"快速了解"时，本步可降级为"质量速览"（仅规模 + 复杂度 Top-5 + 覆盖率 + 一眼可见的问题），但必须标明是速览版。

## Step 6 · 技术栈拆解

**目标**：回答"这套栈还健康吗、基于它做二开的成本在哪"。

方法（详细规范见 `tech-stack.md`）：
1. 填满七维度矩阵：语言构成 / 运行时与版本 / 框架与核心库 / 数据与存储 / 基础设施 / 构建与交付 / 质量与工程化。
2. 提取依赖清单（直接依赖表 + 间接依赖规模），>200 个间接依赖标注"依赖膨胀"。
3. 依赖健康度检查：维护状态、版本过时、已知漏洞（`npm audit` / `pip-audit` / `govulncheck` / `osv-scanner`）、许可证兼容性。
4. 关键选型写三句话评价：是否当前最佳实践、处于什么生命周期、替换/迁移成本。

**必须回答的问题清单**：
- 七维度技术栈矩阵（缺项写"无"并说明）
- 直接依赖表与间接依赖规模
- 漏洞与过时清单（含采集日期，标注"数据截至 X"）
- 本项目与关键依赖的许可证
- 选型评价与二开成本，按 P0/P1/P2 给升级建议

产出：`analysis/<项目>技术栈拆解.md` + `.html`。

## Step 7 · 产物生成

### 形态由接入门决定

| 用户选 | 产出 |
|--------|------|
| `HTML + Markdown`（默认） | 每份报告 `.md` + `.html` 成对产出 |
| `只要 Markdown` | 每份报告仅 `.md`（含 Mermaid 源码 + 纯文本缩进树） |
| `只要 HTML` | 每份报告仅 `.html`（自带完整内容，不依赖 md） |
| `加出 SVG` | 上述任一 + `analysis/svg/<视角>.svg`（每视角一张独立矢量图） |

**形态只改载体，不改分析深度与报告数量。** 规格、选择矩阵与原生候选项问法见 `output-formats.md`。

### 产物清单（按接入门选定的深度档裁剪）

| # | 文件 | 来源 |
|---|------|------|
| 1 | `analysis/<项目>架构实现分析.md` / `.html` | Step 1 |
| 2 | `analysis/<项目>基础层与领域模型演化分析.md` / `.html` | Step 2 |
| 3 | `analysis/<项目>第一性原理与设计巧思分析.md` / `.html` | Step 3 + 4 |
| 4 | `analysis/<项目>代码质量评估.md` / `.html` | Step 5 |
| 5 | `analysis/<项目>技术栈拆解.md` / `.html` | Step 6 |
| 6 | `analysis/<项目>项目全景思维导图.md` | Step 1~6 汇总 |
| 7 | `analysis/svg/<视角>.svg`（可选） | 接入门选了「加出 SVG」时 |

> 用户只要部分角度时，按实际执行范围裁剪清单，但**思维导图与已产出报告必须成对存在**（导图节点不得引用未产出的报告结论）。

### Markdown 报告规范（形态含 Markdown 时）
- 中文，标题层级清晰（≤4 级），顶部写：分析对象、**数据来源**、分析日期、结论先行。
- 表格优先（职责表、指标表、对照表、映射表），代码引用用 fenced code block 并标注文件路径。
- 引用代码必须与仓库现状一致（先读取文件再引用，不凭记忆）。
- 图形用 Mermaid 代码块内嵌，**并同时给一份纯文本缩进版**（宿主不渲染 Mermaid 时仍可读）。
- 自检：`grep -c '^```'` 为偶数（代码块闭合），无 `[TODO]` 残留。

### HTML 报告规范（形态含 HTML 时，重要）
每个 `.html` 必须满足 `html-report-spec.md` 的全部要求，包括：
- 零外部依赖、`file://` 可直接打开
- 统一的深绿主色设计语言（含品牌侧栏、代码框、卡片、时间线、流程图、表格、可折叠巧思卡）
- 左侧 TOC 目录 + 滚动高亮（scrollspy）
- 内嵌轻量 Python/YAML 代码高亮
- 页脚含报告名与互链

推荐做法：复制本 skill 的 `assets/report-template.html` 作为骨架，替换内容区块，而不是从零写 CSS/JS。

### SVG 产物规范（形态含 SVG 时）
- 单文件 `.svg`，`viewBox` 必填，**全部样式内联**（禁 CDN / 外部字体 / 外部 CSS）
- 中文字体栈：`font-family="-apple-system, 'Segoe UI', 'Microsoft YaHei', sans-serif"`；字号 ≥ 11px
- 每张图顶部一行图题：`<项目名> · <视角名>`
- 配色跟随当前 IDE 主题（浅色主题 = 浅底深字）
- 校验：可被 XML 解析器解析；`grep -E 'https?://'` 除 `www.w3.org` 外无命中
- 常用视角与画法见 `output-formats.md` §3.3 与 `mindmap-spec.md`

### 思维导图规范
遵守 `mindmap-spec.md`：
- md 内嵌 Mermaid `mindmap` 源码（节点 ≤14 字、无冲突字符、层级 ≤4）+ 同源的纯缩进树 + 内联 SVG 片段
- HTML 报告内的导图用**内联 SVG**，禁止引 CDN
- 结构顺序固定：定位 → 技术栈 → 分层架构 → 核心链路 → 关键设计 → 质量与风险 → 演化脉络
- 每个节点都必须能在报告中找到出处

## Step 8 · 校验与交付

对每个 `.html` 执行以下校验（全部通过才算完成）：

```bash
python - <<'EOF'
import re, subprocess, tempfile, os
for f in ["analysis/<报告>.html", ...]:        # 逐个文件
    src = open(f, encoding="utf-8").read()
    assert src.startswith("<!doctype html>") and src.rstrip().endswith("</html>")
    assert src.count("<html") == 1 and src.count("</html>") == 1
    opens = len(re.findall(r"<script>", src)); closes = len(re.findall(r"</script>", src))
    assert opens == closes == 1, f"script mismatch {opens}/{closes}"
    m = re.search(r"<script>(.*?)</script>", src, re.S)
    with tempfile.NamedTemporaryFile("w", suffix=".js", delete=False, encoding="utf-8") as t:
        t.write(m.group(1)); js = t.name
    r = subprocess.run(["node", "--check", js], capture_output=True, text=True)
    os.unlink(js)
    assert r.returncode == 0, f"JS error -> {r.stderr}"
    print(f"{f}: OK")
print("ALL CHECKS PASSED")
EOF
```

**思维导图附加校验**：
- Mermaid 源码中除根节点外无 `(` `)` `:` `;` 冲突字符
- 全文件 `grep -nE "src=\"https?://|href=\"https?://"` 无 CDN/外链命中（`www.w3.org` 命名空间除外）

交付清单：
- `analysis/` 下**按接入门选定形态**产出的各报告（架构实现 / 演化 / 第一性原理与巧思 / 代码质量 / 技术栈）+ 项目全景思维导图（+ 可选 `svg/`）
- 用宿主的文件呈现能力（如 present_files）把产物交给用户（HTML 可直接开预览面板）
- 向用户汇报三句话（见 `output-formats.md` §7）：**产物在哪**（含 HTML 打开方式）、**本次形态**（可随时补出其他形态）、**哪些门未经确认**（走了 autopilot 时必须声明）
- 关键结论 2~3 条

## 分阶段执行的约定

- 若用户只要求某一角度（如"分析 git 历史""只看代码质量"），可只执行对应 Step，产物命名与形态规范不变。

- 若用户选"快速总览"，执行 Step 0 + Step 1 + 思维导图，然后**询问是否展开其余步骤**（这是接入门已确认过的深度档，不算打扰）。
- 用户中途订正目标或形态时：**只重跑受影响的下游**（改形态 = 只重跑 Step 7），绝不整体重开（见 `interaction-gates.md` §6）。
- 所有 step 完成前不要声称"分析完成"；校验失败视为未完成。
